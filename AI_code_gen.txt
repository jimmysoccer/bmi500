4. FAILURE-MODE ANALYSIS AND THE GUARD ADDED FOR EACH (requirement 4)
--------------------------------------------------------------------------------

The assistant was asked to assess failure modes *before* coding. Ranked list,
with the guard actually present in matvec_multiply.py and the test that covers it.

#   Failure mode                                   Why it is dangerous
-   --------------------------------------------   --------------------------------------------
1   Non-iterable input ( int, None, object )        Python raises a vague "not iterable"
                                                    TypeError deep inside the loop.
    GUARD: _as_list() catches TypeError and re-raises with the argument name and
           type; bare numbers are rejected with their own message.
    TEST : test_dot_product_rejects_bare_scalar

2   str / bytes passed as "a vector"                Iterating a string yields characters;
                                                    would raise weirdly or, with a matching
                                                    argument length, produce nonsense.
    GUARD: explicit (_STRING_LIKE) rejection with an explanatory message.
    TEST : test_dot_product_rejects_string_argument, test_matvec_rejects_string_matrix_or_row

3   Length mismatch between the two vectors         `zip()` truncates at the shorter input and
                                                    returns a plausible but WRONG number.
    GUARD: len check before any arithmetic -> ValueError naming both lengths.
    TEST : test_dot_product_length_mismatch_raises

4   Non-numeric entries ("3", None, nested list)    "3" * 2 == "33" in Python: the call appears
                                                    to succeed and returns garbage silently.
    GUARD: every entry must be numbers.Number (and not bool) -> TypeError with index + value.
    TEST : test_dot_product_rejects_non_numeric_entries,
           test_dot_product_rejects_nested_lists,
           test_matvec_rejects_non_numeric_vector_entries

5   bool smuggled in as int (True/False)            bool is a subclass of int, so it passes any
                                                    numeric check; True*True == 1 hides a logic
                                                    bug upstream (e.g. a list of comparisons).
    GUARD: `isinstance(value, bool)` -> TypeError.
    TEST : test_dot_product_rejects_booleans

6   NaN / inf entries                               Poison every downstream result; nothing
                                                    raises, the answer just silently becomes NaN.
    GUARD: float entries must satisfy math.isfinite -> ValueError unless allow_nonfinite=True.
    TEST : test_dot_product_nonfinite_guard,
           test_dot_product_allows_nonfinite_on_request,
           test_matvec_nonfinite_propagates_as_error

7   Row length != len(vector)                       A @ x is undefined; zip() would again
                                                    truncate and return a believable vector.
    GUARD: width vs len(vector) comparison -> ValueError naming both numbers.
    TEST : test_matvec_row_length_mismatch_raises

8   Ragged matrix (rows of unequal length)          Column count is ambiguous; later NumPy-style
                                                    refactors would fail unpredictably.
    GUARD: every row must match the first row's width -> ValueError naming the offending row.
    TEST : test_matvec_ragged_matrix_raises

9   Flat 1-D list passed as the matrix              Very common caller mistake ([1,2,3] instead
                                                    of [[1,2,3]]); iterating gives scalars.
    GUARD: each row must be a sequence and not a Number -> TypeError explaining the shape.
    TEST : test_matvec_flat_list_is_rejected

10  Empty matrix with non-empty vector              Undefined combination that would otherwise
                                                    silently return [] .
    GUARD: ValueError; [] is returned only for the consistent case [] @ [] -> [] .
    TEST : test_matvec_empty_matrix_and_empty_vector,
           test_matvec_empty_matrix_with_nonempty_vector_raises

11  Mutating the caller's input                     Side effects are a silent correctness bug in
                                                    numerical code that gets reused.
    GUARD: inputs are copied via list() before validation/computation.
    TEST : test_dot_product_input_not_mutated, test_matvec_input_not_mutated

12  Wrong result that nevertheless "looks right"    No exception, no test failure, wrong science.
    GUARD: main() cross-checks against an independently written reference
           (_reference_matvec, uses sum()/zip, no shared code path) and asserts
           shape, finiteness, and max deviation < 1e-9; the same idea is used in
           test_matvec_large_random_against_reference (200x300 random data).
    TEST : reference cross-check inside main() every run

Deliberate non-goals (documented rather than silently omitted):
  - No attempt to detect ill-conditioned input or catastrophic cancellation;
    float64 rounding-order differences are real and the tolerance used
    (1e-9 absolute in tests, 1e-9 in main) is set accordingly.
  - No automatic flattening/coercion of bad input: the chosen policy is to fail
    loudly (TypeError/ValueError) instead of guessing what the caller meant.
  - 1000x1000 in pure Python costs ~0.4 s for 1e6 multiply-adds; if larger sizes
    are needed later the honest fix is NumPy, not micro-optimising this loop.
